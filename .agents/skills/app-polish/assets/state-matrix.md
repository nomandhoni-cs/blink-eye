# State matrix and QA run template

Use the cases below to select fixtures and environments for one release or important change. Test in local/staging conditions with test accounts, synthetic data, and sandbox transactions. Record what ran in a copy of [qa-run.csv](qa-run.csv), then follow [release QA](../references/release-qa.md). For a review-only task use the [flow audit](polish-audit.md) instead.

**Run scope:** Build/revision · task and entry point · user/role · browser/OS/device · locale, text scale, input/AT · fixture and network mode · expected authoritative outcome. Cross relevant cases with these variants, rather than saying a single screenshot covers the matrix:

- Normal, fast success; slow response and timeout; no network; cached vs. no cached data; restart/back/return. For writes, distinguish failure before commit from a lost response **after** commit.
- New and returning accounts, read-only vs. allowed roles, switched accounts; denied, limited, and revoked access where supported.
- Keyboard/touch, relevant screen reader, visible focus, high text size, narrow layout, sticky bars/keyboard in view, reduced motion, expanded text, RTL and long real strings where supported.

| Case ID | Topic | Priority | Set up and act | Pass only when |
| --- | --- | --- | --- | --- |
| `disclosure-at-commit` | 1 | gate | Open a real review/commit step with approved terms or material disclosure. Navigate at narrow layout and with keyboard/assistive reading. | Material impact and required links/controls are clear before commitment; the approved action has the expected effect. |
| `optional-choice` | 1 | gate | Decline or dismiss an optional data/communications choice. Where applicable, change it later. | No false assent, unrelated access, or forced acceptance to finish the core task; state changes match actual data behavior. |
| `empty-first-use` | 2 | gate | Use an authorized new account with no data and let the load succeed. | The cause is clear; a real start or safe return is available. No fake create path for a read-only role. |
| `empty-filtered` | 2 | gate | Keep underlying items in a list but select a query/filter combination with zero matches. | The UI names the empty cause, preserves query and choices, and offers a useful reset/edit. It does not imply the account has no data. |
| `empty-unavailable` | 2 | gate | Fail a fetch with and without cached data; try reconnect or return. | No misleading zero-state; stale data is identified when shown, and recovery or exit is reachable. |
| `field-help` | 3 | gate | Focus/type in a field with a meaningful rule, use, or audience. If applicable view the resulting data as another authorized role. | Label and needed instructions are visible and associated; stated visibility matches actual audience. |
| `success-record` | 4 | gate | Complete a normal write; revisit result from list/receipt/status after leaving. | Feedback matches the authoritative fact. For consequential action the record and next steps are reachable and perceivable. |
| `queued-resume` | 4 | gate | Queue supported work (e.g. offline); leave, reopen, and allow it to sync or fail. | Local/queued and remote/settled results are distinct. Reopen shows the correct state and a failure has a recovery path. |
| `validation-recovery` | 5 | gate | Submit an invalid field beside valid entries. Correct it and resubmit. | Text identifies the error and safe fix; linked/focus behavior works; safe input remains. No duplicate announcements or previously successful field values lost. |
| `auth-message` | 5 | gate | Exercise applicable sign-in/recovery failures with owned fixture accounts. | The response provides safe recovery without exposing account existence/status or internal details. |
| `unknown-write` | 5 | gate | Suppress a write response before and after actual commit in staging; follow status lookup. | No success or failure is invented. The app reconciles the existing request where supported, or uses a safe fallback rather than blind resubmit. |
| `duplicate-submit` | 5 | gate | Double-tap or retry the same consequential intent during a delayed response. Then perform a new distinct intended action where allowed. | Exactly one effect for the first intent in the fixture; the second intent is not mistakenly suppressed. Check the authoritative record. |
| `load-timeout` | 6 | gate | Compare fast, slow, and stalled work; navigate away during wait or cancel where supported. | Accurate status; only measurable progress reports units; wait resolves or yields a truthful recovery path. Late completion does not disrupt unrelated UI. |
| `load-reduced-motion` | 6 | gate | Wait with motion reduced and check with assistive reading. | State and control remain understandable without animation; no placeholder focus traps or tick-by-tick noise. |
| `reuse-edit` | 7 | gate | Enter a value earlier in the same process. Select/reuse it, change it, and return to the step. | Eligible value is offered and editable; the user sees which one will apply, and current valid value is submitted. |
| `reuse-account-switch` | 7 | gate | With a draft or pending form, sign out or switch test account/workspace. | Prior-user data never appears; no unauthorized draft/reuse claim on resume or in a shared URL. |
| `icon-semantics` | 8 | gate | Use controls and toggles with icon, keyboard/touch, and a screen reader. | Purpose, state, focus and hit area are distinguishable; names describe actions. A decorative glyph is not redundantly read. |
| `icon-consistency` | 8 | follow-up | Compare sibling states/components against the existing icon family and tokens. | Variant differences convey purposeful states or platform conventions; no accidental visual mismatch. Elevate priority if it misleads. |
| `action-label` | 9 | gate | Have someone predict/demonstrate what a decision control does, then compare with actual behavior. | Label distinguishes review from commitment; consequence is accurate and accessible name includes the visible label where applicable. |
| `permission-denial` | 10 | gate | Open the feature, choose the specific access action, deny/dismiss (also test limited grant if supported). | No unrelated early request. Specified scope is minimal; decline or limited scope has clear behavior and no prompt loop. |
| `permission-revocation` | 10 | gate | Grant on a test device, then revoke in settings or let a one-time grant expire. Resume. | App rechecks grant, stops using revoked capability, and provides appropriate fallback/exit without misleading success. |
| `filter-reset` | 11 | gate | Start with query, custom sort, and multiple filters with a current default baseline; remove one, clear, reopen and test Cancel/Apply if batch. | Applied labeling, results and defaults agree. Only promised scope resets; draft Cancel doesn't change applied state. |
| `filter-late-response` | 11 | gate | Have old filtered request resolve after a new reset/search result in a fixture. | Old response cannot overwrite current results, result announcement, count, or applied state. |
| `critical-text-scale` | 12 | gate | On supported small layouts test relevant web resize/reflow or native text scale, with sticky CTA and keyboard. | No essential price/period, visibility, consequence, status, or recovery copy clipped/covered; action remains usable. |
| `critical-text-locale` | 12 | gate | Test expanded and RTL pseudolocales plus relevant real translations and long values. | Important words and formats stay readable in correct order; optional truncation works with real keyboard and touch access. |

## Record results without overstating coverage

- Keep the baseline IDs and topic numbers in the CSV. Baseline gate rows must remain gates; raise a `follow-up` to `gate` when harm warrants it. Add unique lowercase hyphenated case IDs for extra tests. For variants either include all required variants in one case’s evidence or give them separate IDs and gate them as needed. Declare your variant scope; the ledger cannot infer missing variants.
- Use `not-run`, `pass`, `fail`, `blocked`, or `n/a` in `result`. For any disposition except `not-run`, provide `evidence_or_reason`: a test/output pointer plus environment and observed expected/actual result; for `blocked`, what prevents the test; for `n/a`, the scoped reason the case is not applicable and its reviewer. An `n/a` is not a test pass, and a missing fixture is `blocked`, not `n/a`.
- Run the optional [QA helper](../scripts/check-qa.py): `python3 <skill-dir>/scripts/check-qa.py <your-run.csv>`. Add `--json` for structured output. Exit `0` means applicable declared gates were recorded as passed and exclusions documented; `1` means open gates or no applicable gate executed; `2` means structural/data error. Review follow-ups and any exclusions manually before a go decision. No numeric score or verification of the evidence itself.
